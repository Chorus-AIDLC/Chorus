## Why

Chorus already ships three agent-runtime plugin surfaces — Claude Code (`public/chorus-plugin/`, marketplace-installed), Codex (`plugins/chorus/` + `public/install-codex.sh`), and OpenClaw (`packages/openclaw-plugin/`). Amazon **Kiro CLI 2.0** (Apr 2026) added exactly the primitives a Chorus plugin needs — custom agents (`.kiro/agents/`), steering files (`.kiro/steering/`), the open Agent-Skills standard (`.kiro/skills/<name>/SKILL.md`), native remote MCP with static auth headers, native subagents, and lifecycle/tool hooks — so Kiro is now a first-class target. This change is the **plugin surface** child of the Kiro-integration theme (idea `a1e25b50`); the sibling daemon `--agent kiro` backend (`dc53a459`) and the connection/onboarding UI (`4181e7b1`) are separate children.

The binding scope was set by a two-round elaboration on idea `97ccd334` plus a follow-up human instruction. Kiro's real conventions were verified against current docs (7 references on the idea) and differ from the other surfaces in ways that shaped every decision below:

- **Kiro has no "plugin bundle."** It only reads loose `.kiro/{agents,steering,skills,settings}` at either workspace (`<project>/.kiro/`) or global (`~/.kiro/`) scope. So there is nothing to "package" — the deliverable is a **template tree + an install script** that merges it into `~/.kiro/`, mirroring how `install-codex.sh` writes `~/.codex/`.
- **MCP ports ~1:1 from the Claude Code `.mcp.json`.** Kiro remote HTTP MCP accepts a static `headers` block (`Authorization: Bearer ${env:CHORUS_API_KEY}`) — no OAuth dance. It lives in `~/.kiro/settings/mcp.json`; agents pull it in via `includeMcpJson: true`.
- **Skills are the open Agent-Skills standard**, activated by description-match **and** as `/name` slash commands. Content ports ~1:1 from the existing skill roots; only invocation naming and `resources`-wiring differ.
- **Hooks can match MCP tools** (`@chorus/chorus_pm_submit_proposal`, etc.), so the CC/Codex "after submit → nudge reviewer" automation is portable. But hooks live **only inside an agent file** (no standalone `hooks.json`), which is why the design ships a `chorus` main agent to host them.
- **Custom agents do NOT auto-load skills/steering** — each must list `skill://` and `file://.kiro/steering/**` in its `resources` field. Reviewers port to Kiro's **native subagents** (spawned by the main agent, auto-selected by `description`, tool-scoped read-only via `tools: ["read", "@chorus"]`).

## What Changes

- **New template root `public/kiro-plugin/.kiro/`** — the source-of-truth `.kiro/` scaffold, owned by this child (daemon child `dc53a459` reuses it, per elaboration Q `daemon_boundary=a`):
  - `settings/mcp.json` — the Chorus remote MCP server (`type:"http"`, `url:"${CHORUS_URL}/api/mcp"`, `headers.Authorization:"Bearer ${env:CHORUS_API_KEY}"`, `disabled:false`).
  - `skills/chorus-*/SKILL.md` — the ported AI-DLC skills, **all `chorus-` prefixed** for global-install distinctiveness (follow-up human instruction; reverses the round-1 bare-name pick): `chorus-idea`, `chorus-proposal`, `chorus-develop`, `chorus-yolo`, `chorus-review`, `chorus-quick-dev`, `chorus-brainstorm`, `chorus-openspec-aware`. Content ported from the existing roots, adapted to Kiro conventions; intra-skill cross-references (`/proposal` → `/chorus-proposal`) rewritten for self-consistency.
  - `agents/chorus.json` — the **main agent** (Kiro CLI agents are `.json`; Kiro IDE uses `.md` — CLI/IDE split, Kiro#8040): `resources` list every `chorus-*` skill (`skill://`) + steering (`file://`), a `file://./chorus.md` prompt sidecar, `includeMcpJson:true`, `tools` include `subagent` so it can spawn reviewers, and it hosts the **full hook set** (elaboration Q `kiro_agents_set=b` + `hooks_depth=a`).
  - `agents/chorus-code-reviewer.json`, `agents/chorus-proposal-reviewer.json`, `agents/chorus-task-reviewer.json` — read-only reviewer subagents (`tools:["read","@chorus"]`), ported from the CC reviewer files.
  - `steering/chorus.md` — the Chorus AI-DLC project-context steering doc (the CLAUDE.md/AGENTS.md equivalent). **The overview `chorus` skill's content folds in here** rather than shipping a `chorus` skill, so `/chorus` unambiguously means the main agent (no skill/agent slash-command collision).
- **New `public/install-kiro.sh`** — one-shot `curl … | bash` installer, structurally mirroring `install-codex.sh`: verify `kiro`/`kiro-cli` present, collect `CHORUS_URL` + `CHORUS_API_KEY` (env or TTY prompt, non-interactive when both set), and **merge** the template into `~/.kiro/` (global scope by default; `--workspace` writes to `<cwd>/.kiro/` instead). Idempotent, backs up before writing, never blindly overwrites a user's existing `mcp.json`/files.
- **Hooks on the `chorus` main agent** (full parity, elaboration Q `hooks_depth=a`): `agentSpawn`→`chorus_checkin`; `stop`→heartbeat/checkout; `postToolUse` matchers `@chorus/chorus_pm_submit_proposal` / `@chorus/chorus_submit_for_verify` / `@chorus/chorus_admin_verify_task` → nudge spawning the corresponding reviewer subagent. Hook scripts are authored under `public/kiro-plugin/bin/` (Bash-3.2-compatible, CLAUDE.md pitfall #10); the installer copies them (+ `chorus-api.sh`) into `<KIRO_DIR>/chorus-bin/` and substitutes the `__CHORUS_BIN__` placeholder in `chorus.json`'s hook `command`s with the resolved absolute path (so hooks work under both global and `--workspace` scope — this is the fix for the round-1 review BLOCKER).
- **Docs + parity bookkeeping** — register Kiro as the 4th surface: update `docs/MCP_TOOLS.md` references only where surface-count is stated, the `plugin-maintenance` skill (add Kiro to the surface list + bump recipe), and a short `docs/CONNECT_KIRO.md` connect guide paralleling `docs/CONNECT_CODEX.md`.

## Capabilities

### Added Capabilities
- `kiro-plugin-templates`: Chorus SHALL ship a `~/.kiro/`-shaped template tree (MCP config, `chorus-` prefixed skills, a `chorus` main agent, three read-only reviewer subagents, and a steering doc) that lets Kiro CLI drive the full Chorus AI-DLC workflow, with every skill/agent name carrying the `chorus-`/`chorus` prefix for global-install distinctiveness.
- `kiro-plugin-installer`: Chorus SHALL provide an idempotent `install-kiro.sh` that merges the template into the user's `~/.kiro/` (global, default) or `<cwd>/.kiro/` (`--workspace`), wiring the Chorus MCP server with a static bearer header and backing up before any overwrite.
- `kiro-session-automation`: the Kiro `chorus` main agent SHALL carry hooks that check in on spawn, heartbeat/checkout on stop, and nudge the matching reviewer subagent after proposal-submit / task-submit / task-verify MCP calls — the Kiro-native equivalent of the CC/Codex session-automation hooks.

## Impact

- **New files** — `public/kiro-plugin/.kiro/settings/mcp.json`; `public/kiro-plugin/.kiro/skills/chorus-{idea,proposal,develop,yolo,review,quick-dev,brainstorm,openspec-aware}/SKILL.md`; `public/kiro-plugin/.kiro/agents/{chorus,chorus-code-reviewer,chorus-proposal-reviewer,chorus-task-reviewer}.json` (+ `.md` prompt sidecars); `public/kiro-plugin/.kiro/steering/chorus.md`; `public/kiro-plugin/bin/*.sh` (hook scripts + copied-in `chorus-api.sh` + `test-syntax.sh`); `public/install-kiro.sh`; `docs/CONNECT_KIRO.md`.
- **Edited docs** — `docs/MCP_TOOLS.md` (surface count), the `plugin-maintenance` skill doc (surface list + bump recipe). No change to `src/`, Prisma schema, REST API, or the other three plugin roots' content (this surface is additive).
- **No runtime/schema/API change.** Pure plugin-template + install-script + docs delivery.

Out of scope (confirmed): the daemon `--agent kiro` headless backend and its `kiro-cli chat --no-interactive` wake/resume/interrupt (child `dc53a459` — carries the Kiro#5958 headless-MCP-load risk); the connection/onboarding UI + `clientType=kiro` daemon identity (child `4181e7b1`); a native Kiro **Power** (`POWER.md`) wrapper (elaboration deferred it — install-script first); any change to the CC/Codex/OpenClaw skill *content* (only their surface-count bookkeeping is touched).
