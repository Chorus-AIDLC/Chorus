# Personal project Team design

## Authority and storage
Add `ProjectAgentTeam` with company/project/owner relations, unique `(projectUuid, ownerUuid)`, nullable template relation, template display name snapshot, role overrides JSON and effective-members snapshot JSON, revision/timestamps. JSON role maps use the four existing role identifiers and arrays of agent UUIDs; missing override means inherit, an empty array means explicitly empty. Never reference template member UUIDs. Company is enforced alongside owner/project in every query.

Human user-session writes only. Resolve personal owner from `auth.actorUuid` for users and `auth.ownerUuid` for agent reads, never request input. Require project viewer access for configuration/read, editor access for handoff; an ownerless agent sees no team. Agent read additionally follows existing resource permission checks. Hidden targets use normal not-found responses without foreign metadata. Project admin is not a private-Team bypass.

## Module contracts
Shared types in `src/types/project-agent-team.ts`; service in `src/services/project-agent-team.service.ts` owns parsing, scope, membership eligibility, transactions and DTOs. Routes are thin wrappers using existing API response/error conventions.

`GET /api/projects/:uuid/team` returns `{team: ProjectAgentTeamDto | null}`. `PUT` accepts strict `{templateUuid: UUID|null, overrides?: Partial<Record<Role, UUID[]>>}` and saves effective state, with no assignment side effect. Null is accepted only for an existing frozen configuration; initial binding or rebinding requires an owned template. `DELETE` unbinds only this user's configuration. These REST endpoints require human sessions; agents use the shared read service through MCP.

DTO: `projectUuid`, `templateUuid: string|null`, `templateName`, `frozen`, `revision`, `overrides`, `roles` (all four arrays of members), `myRoles`. Each member contains `agentUuid`, `agentName`, `eligible`, `missingPermissions`, `hasProjectAccess`, `online`, `activeCount`. Exact concrete revision representation may be an ISO update timestamp or monotonic integer but is opaque to callers. `myRoles` lists the calling agent's valid memberships; role arrays retain ineligible bindings with flags. No templates or memberships belonging to other owners leak.

Expose `getProjectAgentTeam(auth, projectUuid, client?)` for shared reads; optional `ProjectTeamClient` uses the repository's extended Prisma transaction type. Existing agent liveness lookup supplies online/load through that same client. Checkin adds a separate `projectTeams` map for the union of active project UUIDs and request-scoped project UUIDs, bounded by that set, leaving `activeProjects` counts unchanged. Direct `chorus_get_project_team({projectUuid})` handles projects outside this set and returns `{team: DTO|null}`. Register project:read and project visibility checks in permission/collection contracts; a team detail is not a paginated collection.

## Inheritance and eligibility
Retention is evaluated against the current effective pre-save membership in the transaction, not the historical snapshot. Request override lists have at most 200 total tuples, separately from the template's own limit. Effective snapshots preserve their full union (which may exceed 200) on freeze and subsequent reads/saves; input limits must not silently discard persisted memberships.

Compute effective memberships from current owned template plus whole-role overrides at read time. Each newly applied effective tuple must be an owned, same-company agent with the role's existing minimum permissions and sufficient project access (editor is required to collaborate, including comment-only reviewers). Retained drifted tuples can be displayed, retained or removed without granting authority; a tuple removed then re-added must pass checks. A fresh binding/rebinding validates all effective members. Distinguish connectivity from eligibility: offline leads may be selected manually, but offline is displayed.

Before template deletion, materialize current effective memberships for every referencing personal configuration in the same transaction; null the template and persist the display name. Frozen reads use this snapshot, still filtering deleted/foreign agents and rechecking permissions/access. Do not trigger assignment. Template edits need not fan out membership rows; live reads use the current template. Synchronize template mutation and project writes with serializable transactions/bounded retries to avoid deletion/save races. Account for template revision in preview validity, not just project configuration revision.

Frozen saves prune deleted or no-longer-owned references from server-owned snapshot and retained role maps inside the existing transaction. Submitted overrides and live template members still require same-company ownership/existence; do not silently discard invalid client input. Permission-drifted existing own members remain visible and ineligible. The editor exposes missing explicit-override UUIDs immediately (without foreign names or an unrelated dirty-state edit) so the owner can remove them deliberately.

## Explicit handoff
Persist the last confirmed handoff recipient on the personal configuration independently of current memberships. DTO `handoffWarning` is null or contains that own recipient's UUID/name and a reason (`removed_from_lead`, `ineligible`, `deleted`), whenever it ceases to be a valid lead. Keep the warning visible even when another eligible lead remains; do not infer safety solely from current role arrays. Clear/update it only on explicit successful repair handoff or unbind. The UI shows the warning and offers editor-authorized explicit preview/repair, never automatic reassignment. Deleted identities must not leak foreign metadata.

`POST /api/projects/:uuid/team/handoff` accepts `{leadAgentUuid, preview: true}` or `{leadAgentUuid, confirmationToken}`. Require human user, editor access, owned current eligible lead and selected existing config. Preview returns exact candidate identities/titles, count and an expiring server-verifiable token bound to caller/company/project, lead, effective team/eligibility revision and candidate current assignments/stages. Recompute under transaction at confirm, reject stale/mismatched/expired preview with conflict and no changes. This can use the existing preview token pattern; never trust caller-provided candidate UUIDs alone.

Candidates: same-project Ideas whose current assignee is the user, their same-company agents or instances of those agents; exclude unassigned, foreign assignees, terminal/derived-done Ideas. Reuse existing derived-status semantics (including theme child rollups) rather than raw stored `elaborated` status. No arbitrary discovery cap. Preserve elaboration/proposals and in-flight Task assignments/status/sessions; assigning an open Idea follows existing open-to-elaborating semantics. Resolve fixed project CWD/instance preferences using existing assignment helpers and record assignment provenance. Commit candidates atomically with conditional race checks; do not invoke the existing nontransactional assignment helper in a loop. After commit emit ordinary assignment activity/notification/wake for changed logical assignees, deduplicated; already-selected lead assignments are no-ops preserving pins. This is explicit user assignment, not automatic role routing. No background Team change reassigns an Idea.
