# Chorus v0.19.1：新增轻量 Research 与行内证据引用

给 Agent 一个“接入某个平台，批量导出数据”的想法，它很快就能列出接口封装、任务队列、导出页面，连验收标准都写好了。

但那个平台的 API 允许批量读取吗？需要哪一级授权？文档里的限流规则适用于当前版本吗？这些问题如果靠印象回答，整份方案就建立在几个还没查过的前提上。等开发到一半才发现限制，前面的任务拆分也得跟着改。

Chorus v0.19.1 加入轻量 Research 和行内证据引用，让 Agent 在澄清需求、准备方案时查清关键事实，并把依据留在结论旁边。

## 先找出哪件事需要查

Research 从一个具体问题开始：这个事实会影响哪项决定？

比如 API 的读取权限会影响接入方式，已有 SDK 对某个版本的支持情况会影响技术选型。这些可以查官方文档、源码或其他相关资料。至于第一版要支持多少用户、是否接受额外成本，仍然需要人来决定。

创建 Idea 时，可以勾选先做 Research。没有勾选时，Agent 仍会根据事实缺口判断是否需要查证；明确要求跳过，就会跳过。已有信息足够时，流程直接继续。

到了 Proposal 阶段，Agent 会先复用 Idea 中已有的研究结果。只有设计过程中出现了新的事实问题，才补充调查。同一轮工作恢复执行、收到一条评论，或者从 brainstorm 返回，都不应该成为从头再查一遍的理由。

## 查到能支持决定，就停下来

一次 Research 围绕一个问题展开。技能要求 Agent 以大约 2–5 分钟为预算，最多深入阅读 5 个相关来源，优先使用官方、原始和版本匹配的资料。这是 Agent 的执行约束，实际耗时也受检索工具影响。

没有来源数量的下限。一份官方文档已经回答了问题，就不必再找四篇文章凑数。工具不可用、资料互相矛盾，或者查完仍然没有答案，也要如实留下限制和未知项，交回原来的工作流。

有用的结果会进入现有 Idea 或方案文档：查到了什么，对当前决定有什么影响，还有什么没有确定。进入下一阶段时，接手的 Agent 可以沿着这些记录继续判断。

## 结论旁边，直接看到依据

查过资料，还需要让读方案的人知道每个判断对应哪份证据。

v0.19.1 支持在 Idea、Proposal、Task、Document 和评论的 Markdown 中插入行内引用。Agent 先保存或复用真实的证据记录，再用它的 UUID 写出引用：

```markdown
这项接口需要额外授权。[1](ref:<证据的 UUID>)
```

阅读时，引用会显示成紧凑的 `[1]` 标记。鼠标悬停或键盘聚焦，可以查看证据标题、类型、链接和备注；点击后直接打开来源页面。

这样审阅方案时，看到一条会影响设计的判断，就能顺着它找到依据。证据记录被删除后，引用标记仍然保留，并提示证据不存在，方便发现需要重新核实的地方。

## 方案已经写了，也可以补查

事实问题不一定在创建 Idea 时就能想到。有时澄清已经结束，甚至方案已经批准，才发现还需要确认一个外部限制。

只要实际开发尚未开始，就可以从 Idea Tracker 的操作菜单发起 Research。方案已批准、任务还没开工，也在这个范围内。请求会进入该 Idea 原来的会话，按队列执行，结果继续补充到原有内容中。

这次菜单操作的边界也很明确：查证、保存有用的发现，然后结束。它不会重置已经回答的澄清问题，也不会顺手启动开发。如果新事实影响了已批准的方案，Agent 会记录影响和需要调整的地方，交回原有流程处理。

为了让这些操作更容易辨认，这一版也为 Idea 创建和 Research 增加了专用 daemon 事件。会话里能区分正在创建 Idea、执行 Research，还是处理普通消息；支持新协议的客户端会分别排队执行这些操作，旧客户端继续通过兼容路径工作。

## 升级

更新 Chorus CLI，然后按提示更新所用 Agent 的集成：

```bash
npm install -g @chorus-aidlc/chorus@0.19.1
chorus agents add
```

更新后重启对应 Agent。
