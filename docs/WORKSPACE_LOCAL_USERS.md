# Local workspace accounts

Chorus supports explicitly local username/password workspaces alongside existing OIDC workspaces. Accounts and credentials belong to one workspace; a username or email may repeat across workspaces. Existing non-OIDC workspaces and the deployment-level `DEFAULT_USER` development fallback are **not** automatically converted to local workspaces.

## Initialize and administer

1. Sign in to the Superadmin console and choose **Create company → Local username and password**.
2. Enter the workspace name and first administrator's username and email. Display name is optional, just like subsequent invitations.
3. Copy the resulting invitation URL **before leaving**. Share it only with its intended recipient through a trusted channel. Chorus does not automatically send email or require SMTP for this flow.
4. The recipient opens the single-use link, sets and confirms a password, then returns to the normal login page. This does not automatically sign them in.
5. All ordinary login starts with a username or email, including deployments with `DEFAULT_USER` enabled. If it identifies multiple workspaces/roles, select the intended candidate; a single match skips selection. Only then enter the password or continue to the selected workspace's SSO redirect. There is no separate SSO entry or password-first fallback. For SSO discovery, enter the configured work email; SSO identity management remains with the IdP. To change the identity, return to discovery; the password is cleared.
6. An active local Workspace Admin can open **Settings → Workspace users** to invite users, edit identity, enable/disable, reset credentials, grant/revoke Workspace Admin or remove users.

Before the first administrator activates, the Superadmin workspace detail page shows the pending identity and allows confirmed reissue, revocation or atomic replacement. Reissue invalidates the old link. Revocation removes the pending account and leaves setup awaiting a replacement invitation. Replacement uses a new UUID even with the same username/email; nothing is inherited from the old account. These operations serialize with acceptance and reject stale identity selections. Once initial setup has been activated, this panel is read-only; deleting the account later does not reopen Superadmin setup recovery. This is not a Superadmin password-reset bypass or daily-user administration.

The first release has one fixed administrative capability, **Workspace Admin**, not configurable RBAC. Ordinary accounts retain Chorus's existing project/business access model. Workspace Admin does not bypass private project or project-group access. Superadmin creates the workspace and first administrator; this feature does not add global daily user administration.

## Passwords and credential recovery

Passwords use bcrypt with work factor 12, at least 8 Unicode characters and at most 72 UTF-8 bytes, with no uppercase, digit or symbol requirement. The invitation/reset page shows live requirement progress; password and confirmation inputs have independent show/hide buttons matching the existing Superadmin sign-in interaction. Password hashes never appear in user DTOs. Invitation and password reset links expire after 24 hours. Links contain random opaque credentials, while only SHA-256 hashes are stored. Issuing a replacement invalidates the old link. Links bind to the account/workspace and credential generation; expired, consumed or superseded links fail generically.

An administrator issues password reset links from the user list and delivers them through a trusted channel. Issuance and acceptance revoke existing local sessions. A password-only reset does not permanently destroy Agent API keys; active-owner keys remain subject to current owner eligibility and project access. No self-service registration or forgotten-password email flow is added.

Disabling an invited account invalidates its link. Enabling that passwordless account returns it to **Invited** with a new link; it is not active until acceptance. Enabling an account with an established password permits a new login, but does not revive revoked sessions. Disabled accounts cannot accept reset links to reactivate themselves. Keep another active administrator available for recovery; there is no unauthenticated or Superadmin bypass added for a lost last-admin credential.

Credential issuance returns only the controlled `/login/local/accept?token=…` path. All invitation/reset copy interfaces build the full link with `window.location.origin`, preserving the domain/CNAME, scheme and port currently open in the browser. Issuance does not depend on `APP_URL` or trust incoming Host/forwarded headers. The UI validates the path and token before attaching the current origin; no server-provided external origin is copied. API-only callers must resolve the relative path against their chosen public frontend origin. Acceptance pages use no-referrer metadata and remove the token query from the address bar after loading. Do not copy credential URLs into public tickets, screenshots, logs or work reports. Next development request logging excludes the acceptance URL. Configure production reverse-proxy/access logs to omit or redact its `token` query parameter; frontend no-referrer does not redact infrastructure logs.

## Revocation, historical attribution and safety

Every local session request reloads the user and workspace, checks active status and generation, and uses the current administrative flag. Already-open event/notification SSE connections use committed `account_access_changed` broadcasts and a 30-second monotonic authorization lease. Ordinary deliveries check only in-memory validity, known credential expiry and the lease deadline; they do not repeat full authentication or write API-key `lastUsed`. Relevant user/owner/Agent/key changes trigger authoritative state checks, not unconditional closure (new sessions and active-owner keys survive password-only resets). Connections register before their initial state check, suspend queued deliveries during checks, and clean up listeners/timers on failure or cancellation. Lightweight indexed reads normally start after 25 seconds, ahead of the existing 30-second heartbeat; the lease is measured from query start, not completion. Delayed timers, hung checks or missed best-effort Redis broadcasts cannot authorize delivery past the 30-second deadline. This intentionally accepts a bounded cross-instance revocation window, not per-message authoritative revocation. Existing project/group resource gates remain independent. Disable, remove, reset and administrative privilege changes invalidate older sessions. Removed users become tombstones: their UUID remains for historical assignment/activity attribution, credentials are cleared and login is denied. Removal atomically releases the normalized username and login email for reuse in that workspace. Reinviting the same identifiers creates a new UUID and new credential link, without inheriting the old administrator flag, project/group memberships, Agent ownership, keys or history. The deleted UUID retains historical attribution and display email; its login identifiers are null, and its public deletion response has an empty username and the preserved display email. Old sessions, links and owned-Agent keys remain invalid even after the replacement account activates. Active, invited and disabled accounts still reserve their identifiers.

Owned Agent/API-key authentication checks the owner's existence, workspace and active eligibility centrally, including REST and MCP. Disabled/removed owners cannot continue through their keys. Keys do not acquire human Workspace Admin privileges; ordinary active owners retain allowed preset/custom business permissions. Private project/group access continues to be bounded by the owner through the existing authorization model. Unowned agents are unchanged. Owner disabling is a state-based revocation, so enabling an established owner can restore otherwise-valid key eligibility; old user sessions remain invalid.

Lifecycle transactions lock the workspace row, reload actor and target, and protect the last effective administrator. Workspace-admin mutations also protect the sole bootstrap invitation. Only the authenticated Superadmin preactivation setup panel may revoke/replace that pending invitation; it cannot bypass the protection for an activated administrator. Audit records store actor, action and target UUIDs, not credentials. These guards are authoritative server-side; hiding navigation is not authorization.

Discovery intentionally shows only applicable workspace names/UUIDs and the existing OIDC configuration, not member profiles or administrator status. Discovery/login/acceptance have bounded process-local limits. Without a trusted client address, limits are scoped only to the normalized discovery identifier, tenant+login identifier, or hashed acceptance token: there is no shared unknown-address bucket blocking unrelated users.

Leave `AUTH_TRUST_PROXY` unset unless the application is reachable **only through an enforced trusted proxy chain**, with no direct-access bypass. For a single ALB using its default XFF append mode (or one proxy overwriting XFF), set `AUTH_TRUST_PROXY=true`; the default `AUTH_TRUST_PROXY_HOPS=1` selects the validated **rightmost** address, not a client-controlled prefix. For additional trusted append proxies, explicitly configure the actual right-hand hop count (integer 1–16); a wrong count can select an attacker-controlled value or a shared proxy IP. Invalid/missing addresses or hop counts fall back to identity-only limits. IPv4/IPv6 addresses are normalized, including ALB's optional client-port representation. Do not enable this trust mode for ALB preserve mode or a proxy chain that does not append/overwrite XFF reliably.

For CloudFront → ALB in append mode, XFF `client, cloudfront` needs `AUTH_TRUST_PROXY_HOPS=2`, selecting `client`; a spoofed prefix must remain to its left. `.env.example` leaves trust disabled. CDK configures one trusted hop for its ALB-only topology, whose ECS ingress is ALB-restricted. CDK's CloudFront mode sets two hops but leaves trust disabled: its private ALB listener also accepts VPC traffic, so the operator must close that CloudFront bypass before enabling trust. Malformed local login bodies are rejected immediately without credential checks or a shared `invalid` bucket.

**Production and multi-instance deployments need a shared upstream rate limiter** for identity rotation (including password spraying), proxy bypass and sustained attacks. Identity-only fallback does not prevent one client trying many different accounts; bcrypt cost is not a substitute for edge limits. Each schema-valid login attempt performs a bcrypt comparison, including unknown/ineligible identities; apply edge limits before application credential work. As an initial deployment baseline, consider at most 60 credential requests per client IP per minute with a burst of 10, then tune using CPU capacity and shared-NAT traffic; this is an operator-configured example, not an implemented shared limit. Acceptance checks token validity and account eligibility under the workspace lock before hashing a password, so random, expired, used or stale tokens do not trigger bcrypt. In-memory counters are neither shared nor durable across restarts. The fallback is capped at 10,000 buckets with least-recently-used eviction rather than globally denying all new identities at capacity; under sustained cardinality pressure, evicted limits can reset. It is best-effort defense, not a substitute for edge enforcement.

New human assignment candidates contain only active, undeleted users in the workspace. The server checks the same eligibility for new task/Idea assignment, project/group membership creation and role promotion, even when called directly with an old UUID. Existing inactive members may still be demoted or removed subject to the unchanged automatic/last-admin protections; historical attribution and stored memberships are not transferred to a replacement account.

**Targeted lockout trade-off:** without a trusted address, the login bucket is shared by all callers of the same workspace+identifier. The default 10 attempts per minute can therefore be exhausted by someone repeatedly submitting incorrect passwords for a known identifier, temporarily blocking that person's legitimate login; sustained attempts can repeat this denial each window. This does not disable or delete the account. A shared edge limiter with validated client attribution and abuse controls must address this risk before requests reach the application; a generic per-IP limit alone cannot guarantee protection against distributed targeted attempts. Do not enable untrusted forwarding headers or restore a global fallback bucket as a workaround.

## Repeatable isolated verification

Use a disposable database and application process, never the live `.env`, `.pglite`, production database or normal port 8637. The verifier requires an explicit isolation gate, loopback URLs and database port 5435:

```sh
LOCAL_USERS_TEST_ISOLATED=1 \
LOCAL_USERS_TEST_URL=http://localhost:8640 \
LOCAL_USERS_TEST_DATABASE_URL='postgresql://postgres:postgres@127.0.0.1:5435/postgres?sslmode=disable' \
LOCAL_USERS_TEST_ADMIN_EMAIL='<test admin email>' \
LOCAL_USERS_TEST_ADMIN_PASSWORD='<test admin password>' \
node scripts/verify-local-users.mjs
```

Apply migrations to that disposable database first and run Next with the same database, test Superadmin credentials and `NEXTAUTH_SECRET`. Set `COOKIE_SECURE=false` only for the disposable HTTP stack. `APP_URL` may deliberately use a different origin to verify that copied local credential links do not depend on it. Set `CHORUS_USE_PGLITE=1` for a PGlite server; its pool is intentionally single-connection. Fixtures are clearly prefixed and retained for inspection. The verifier never prints raw invitation credentials or keys. It exercises actual HTTP responses/persistence, including concurrent requests; PGlite's single-connection execution is **not** evidence of PostgreSQL multi-connection lock contention. Use a separate PostgreSQL concurrency run when validating a deployment's locking behavior.

Run `node scripts/verify-local-users-browser.mjs` with the same isolation flag, app URL and test admin credentials. Set `LOCAL_USERS_PLAYWRIGHT_MODULE=/path/to/playwright` if Playwright is supplied externally. The browser verifier seeds both the locale cookie and localStorage (the client preference is authoritative), tests English/Chinese in light/dark themes, and writes screenshots only under ignored `.playwright-mcp/` with credential fields masked. The browser verifier includes preactivation reissue/replacement/revocation/recovery, optional display names, previous-link rejection and activation authority closure. `node scripts/verify-local-users-cname.mjs` uses the same isolated settings on port 8640 and maps a test-only `chorus-cname.test` browser alias to loopback; it checks real copied links and acceptance on that alias, without modifying DNS or system hosts. It creates a temporary self-signed HTTPS loopback proxy on an ephemeral port so clipboard checks use a genuine secure context; OpenSSL is required. Browser certificate bypass is test-only, not production TLS evidence, and the proxy/certificate directory are cleaned in `finally`. Run browser and HTTP verifiers sequentially against PGlite to avoid independent database clients interleaving its single-connection protocol. Automated tests and reports must record actual outcomes. The encrypted `docs/design.pen` can only be updated through Pencil MCP; unavailable tooling must be disclosed rather than raw-editing it.
