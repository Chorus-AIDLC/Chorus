## Why

A user @-mentioned **Admin Claude** at `/home/ubuntu/dev/ai-pm` (picked explicitly in the secondary instance picker), but the daemon that actually woke and answered was the one at `/home/ubuntu/dev/strands-ai-sdk`. Both instances were online, the pick was correct, and the pin was written into the mention markup and decoded correctly server-side. The wrong cwd still answered.

The root cause is **not** the `originConnectionUuid` write-once invariant (the original analysis misattributed it). It is that the **daemon-side live wake for `mentioned` is an agent-wide broadcast that never reads the pin**:

- The notification SSE stream is per-agent, not per-connection (`src/app/api/events/notifications/route.ts` subscribes `notification:agent:{agentUuid}`). **Every** online `(host, cwd)` connection of that agent receives the same `new_notification`.
- Each daemon independently routes it (`cli/event-router.mjs` `#fetchAndRoute` → `#resolveAndEnqueue`), and because `mentioned ∈ WAKE_ACTIONS` (`cli/prompts.mjs`), **every** online daemon enqueues a wake. This path reads neither the pin's `(host, cwd)` nor the session origin — whichever daemon wins answers.
- PR #354 made the **server-side** turn creation pin-aware (`notification-turn.ts` `resolvePinnedTarget` + `selectOriginConnection` resolve the pin to a matching online connection and stamp the session origin there), but it never touched the daemon-side broadcast wake. So today the pin governs **which session the turn attaches to**, not **which daemon wakes and answers**.

The same gap silently degrades PR #354's headline `task_assigned` pin: `Task.targetHost/targetCwd` is honored at server-side turn creation but **ignored by the daemon-side live wake** — a pinned task dispatch misroutes identically whenever the agent has 2+ online instances (PR #354's single-online-instance e2e never exercised this).

The fix already exists for one path: the UI-typed `human_instruction` wake is delivered via an **origin-only `deliver_turn` control ping** (`daemon-instruction.service.ts` + `daemon-control.service.ts` + `cli/control-handler.mjs`) that targets exactly one connection by `targetConnectionUuid`, and `cli/event-router.mjs` explicitly suppresses the broadcast wake for `human_instruction` (its comment names the exact "fan the wake out to EVERY connection rather than the session's origin" failure). This change extends that proven pattern to the two pinned autonomous wakes (`mentioned`, `task_assigned`) and to the proposal-writing wake (`elaboration_verified`).

## What Changes

- **Server emits a directed `deliver_turn` ping for a pinned/origin-resolved autonomous wake.** When `maybeCreateTurnForWakeNotification` creates a turn for a `mentioned` or `task_assigned` wake and the selected origin connection is the pin-matched one (or, for `elaboration_verified`, the idea's existing session origin), it emits a `deliver_turn` control ping on that connection's `control:{connectionUuid}` channel carrying the precise `turnUuid` — reusing the exact `human_instruction` keystone.
- **`deliver_turn` carries the wake trigger so the daemon builds the right prompt.** Today `control-handler.mjs`'s `deliverTurn` only re-derives `human_instruction` turns. The pending-turn read + re-dispatch is widened so a `mentioned` / `task_assigned` / `elaboration_verified` turn delivered by uuid runs with its own action prompt (`buildPrompt`), not the human-instruction body.
- **Daemon suppresses the broadcast wake for a pinned autonomous wake.** `cli/event-router.mjs` currently early-returns only for `human_instruction`. It is widened so a `mentioned` / `task_assigned` notification that was delivered (or will be delivered) via the directed `deliver_turn` path is **not** also woken from the agent-wide notification broadcast — the same anti-double-execution, anti-fan-out guard the human-instruction path already has. An **un-pinned** `mentioned` / `task_assigned` wake (no pin recorded) keeps today's broadcast→online-first behavior unchanged.
- **`elaboration_verified` (Verify Elaborate → write the proposal) is directed to the idea's existing session origin.** `Idea` has no pin columns, so this wake has no pin source today and lands online-first. It is directed to the cwd where this idea's conversation already lives (`DaemonSession.originConnectionUuid` for the idea-anchored session); when no session exists yet (the idea was elaborated entirely in the UI and the daemon was never woken), it falls back to online-first exactly as before. No new column, no new UI.
- **Offline pin = plain notification, no wake** (a deliberate change from #354): when the pinned `(host, cwd)` has no online match, no turn and no directed ping are created and the notification stands as the plain record — this change does **not** silently re-route to another cwd. This **reverses** #354's documented "offline pin → online-first fallback" behavior for a *pinned* wake (elaboration Q2: 只记通知、不唤醒); the spec delta MODIFIES that requirement accordingly. (The picker only lists online instances, so a chosen-then-dropped pin is a narrow TOCTOU race, not a normal path.) An **un-pinned** wake is unaffected and still goes online-first.
- **Cross-cwd mention opens a per-instance session.** When a `mentioned` pin resolves to a `(host, cwd)` different from the idea's existing session origin, the directed wake targets a session keyed per-instance (`(agentUuid, sessionId)` where the cwd participates) so each `(host, cwd)` keeps its own cwd-bound transcript — never re-pointing an existing session's origin to a different directory (which would `No conversation found` on `--resume`).

## Capabilities

### Modified Capabilities

- `daemon-cwd-instance-addressing`: the existing requirement *"The autonomous wake SHALL honor a pinned cwd and fall back to online-first"* currently constrains only the **server-side connection selection**. It is rewritten to also require **directed live delivery** — that a pinned `mentioned` / `task_assigned` wake reaches ONLY the pinned online connection (via the `deliver_turn` control ping) and that non-target online connections SHALL NOT also wake from the agent-wide broadcast — closing the daemon-side half of the same capability.

### New Capabilities

- None strictly new; the delta is expressed as additions/modifications to `daemon-cwd-instance-addressing` plus an ADDED requirement covering the `elaboration_verified` origin-directed wake.

## Impact

- **Server**: `src/services/notification-turn.ts` (emit a directed `deliver_turn` after creating a pinned/origin-resolved turn; thread the trigger), `src/services/daemon-control.service.ts` (the `deliver_turn` wire payload already exists — confirm it carries enough to re-derive a non-instruction turn), `src/services/daemon-instruction.service.ts` (the existing `deliverTurnPing` helper is the reuse point). Plus the `elaboration_verified` origin-resolution in `notification-turn.ts` / `elaboration.service.ts` provenance.
- **Daemon (CLI)**: `cli/event-router.mjs` (widen the broadcast-suppression guard from `human_instruction` to any directed-delivered pinned wake; widen `dispatchPendingTurn` so a delivered `mentioned`/`task_assigned`/`elaboration_verified` turn re-derives its own action prompt), `cli/control-handler.mjs` (the `deliverTurn` callback already routes by `turnUuid`; ensure it does not assume `human_instruction`).
- **Reused unchanged**: the `control:{connectionUuid}` reverse channel + `targetConnectionUuid` double-check (子3), `DaemonConnection` identity key, `effectiveStatus` / `STALE_THRESHOLD_MS`, the persisted-turn reconnect-backfill durability net, the `claude --resume` cwd/host binding constraint.
- **No new permission bit. No DDL** (the `elaboration_verified` path reuses the existing `DaemonSession.originConnectionUuid`; `mentioned`/`task_assigned` pins already persist via mention markup / `Task.targetHost`/`targetCwd`).
- **Tests**: unit coverage for the directed-delivery emission on a pinned wake, the broadcast-suppression guard for a delivered pinned wake, the un-pinned fall-through (still broadcast→online-first), the cross-cwd per-instance session, and the `elaboration_verified` origin-directed delivery + online-first fallback. A daemon-integration test asserting only the pinned connection wakes when 2+ instances are online (the exact scenario PR #354's e2e missed).
