## Package compatibility prerequisite

The latest human comment `23315604-0e8b-4d37-aaad-682a69e0fcf0`, recorded in Round 3, retains legacy support and supersedes Round 2's Pi-1-only choice. The package currently declares `>=1.0.0 <2.0.0`; changing installation logic alone cannot fulfill this requirement.

The first task owns compatibility of the **current Chorus package artifact**, preserving the Pi 1.x implementation while adding bounded host-API fallbacks when needed. It must test Pi 0.84.4 and 0.87.1 with adapter, native-MCP boundary 0.99.0 without adapter, and Pi 1.0.2 without adapter. Pi 0.84.4 is the proposed maintained floor, anchored in the previous workspace SDK; versions below it, prereleases, or unsupported major versions must not be advertised as supported. These are required SDK tests with the actual packed extension and bundled subagent loader, not mocked event callbacks. Isolate each SDK's dependency resolution, resource directories, MCP fixture, and dummy credentials so success under the workspace's 1.0.2 dependency cannot masquerade as a legacy result. Record the exact adapter version used, verify its peer/engine compatibility on both legacy fixtures, and make installer tests use the same adapter selection policy. Do not assume an unbounded future adapter release preserves old Pi support.

Audit changed host surfaces such as tool discovery (`ctx.tools` in the current dispatcher), model/thinking inheritance, lifecycle events, reviewer dispatch, and MCP tools. Fallbacks must use APIs verified on that SDK and maintain the query/checkin/comment allowlist; missing discovery must not grant all tools or silently disable required functionality. Test a local-fixture read-only MCP call, session lifecycle, subagent startup, and each shipped reviewer's permitted query/comment and denied business mutation. Legacy gateway-only transports do not regain workflow input parsing: configure/test adapter direct tool exposure for workflow reminders and document that mode. Native codemode and direct child-event reminders retain their existing tests.

After all mandatory fixtures pass, declare the tested compatibility policy in one CLI-consumable module and align package peer metadata to the intended `>=0.84.4 <2.0.0` range, with Node/engine constraints documented. Pack/check the same artifact tested by the fixture matrix. Keep the workspace development resolution at Pi 1.0.2 and avoid unrelated lockfile changes. Do not merely widen the peer string or pin an untested old Chorus release. No publish is authorized in this task; the packed candidate establishes compatibility before coordinated release. If compatibility cannot be implemented or a required SDK/adapter cannot be tested, the task remains unverified and downstream CLI work cannot be accepted; surface the technical gap rather than dropping the human's legacy requirement.

## Shared decision contract

Backend classification describes host MCP capability separately from package support. The CLI task consumes the first task's verified host and adapter policy. For a stable version outside the maintained package range, return an explicit unsupported/incomplete result without package commands; do not present latest Chorus as loadable on that host. Unknown probes retain the safe behavior below but never claim completed MCP setup.

Introduce a small injectable CLI helper, tentatively `cli/init/pi-mcp-backend.mjs`, used by install and upgrade. A bounded, non-interactive `pi --version` probe returns `{ mode: "native" | "legacy" | "unknown", version: string | null, reason: string }`. Accept an unambiguous numeric major.minor.patch version, optionally `v`-prefixed and with build metadata. Compare numeric components, never lexicographically. Stable >=0.99.0 is native; stable older versions are legacy. Prereleases, malformed/ambiguous output, timeout, spawn errors, or unsuccessful exit produce unknown and actionable diagnostics. Do not extrapolate a prerelease's capabilities from its numeric core.

The install-state reader retains raw `chorusPiInstalled` and `adapterInstalled` booleans. Derive completion with the backend decision at the install boundary, not from the presence of both packages alone. Detect exact npm identities, including pinned and object-form sources, without treating similarly named unrelated packages as the adapter. Respect `PI_CODING_AGENT_DIR` and the upgrade target directory.

| Mode | Install/update eligible components | Completion |
| --- | --- | --- |
| native | Chorus only, never adapter | Chorus operation succeeds; migration warnings remain explicit |
| legacy | Compatibility-policy adapter then Chorus | Host is supported and both required components succeed |
| unknown | Chorus only; no adapter mutation | Explicitly incomplete MCP setup with version-probe/manual guidance |

Preserve existing no-binary UNSUPPORTED behavior with conditional manual instructions and zero package commands. Unknown detection is not a silent legacy fallback. Do not abort unrelated agent upgrades; retain existing aggregate partial-failure reporting. Native idempotent re-runs can be SKIPPED when Chorus is present, but still include migration warnings.

Upgrade keeps its established capability probing for targeted updates and noninteractive install. Never use all-extension `pi update`, remove pins, or update unrelated packages. Legacy adapter refresh stays within the first task's validated adapter policy; a policy pin is not an accidental incomplete latest upgrade, while an incompatible user constraint requires a diagnostic and must not be silently rewritten. Native adapter constraints do not affect completeness, because that component is not managed in native mode. Failure of an eligible component is not success. Warnings and capability errors must remain visible alongside the existing status/detail contract.

## Migration and credentials

Read known global and current-project Pi settings to detect configured adapters (string/object/pinned npm sources) and explicit `-builtin:mcp` filters. Never scan or modify arbitrary other projects. On native Pi, explain that an adapter replaces native MCP and offer manual removal guidance, including the appropriate local/global scope, without executing it. If native MCP is explicitly disabled, explain that the user must re-enable it before expecting native tools; do not install an adapter to override that choice. If relevant configuration cannot be read safely, report uncertainty rather than claiming no conflict. Package setup success is not a successful live MCP connection.

Keep MCP headers environment-referenced (`Bearer ${CHORUS_API_KEY}`), preserve other server entries and custom settings, and avoid logging secrets. Native Pi keeps global `mcp.json` and project `.pi/mcp.json`, preserving default codemode exposure. The validated legacy adapter 5.0.0 instead reads `mcp-adapter.json`; its installed `config.ts` explicitly warns that older Pi no longer auto-loads the former `mcp.json` [3](ref:4ba9e467-708c-4a5e-8369-59039a739f08). Accordingly, legacy credential seeding writes the adapter's primary file under the same agent-dir override. Only when this primary file is absent may it seed from the old `mcp.json`; an existing primary always wins, and unreadable/malformed files must not be treated as absent. Preserve unrelated servers and explicit exposure choices. Fresh legacy Chorus entries use `directTools: true`; an existing explicit server/global direct-tools choice is not overwritten. Sanitize the Chorus Authorization/bearerToken to the environment reference before writing the new 0600 file. Leave the old file intact rather than deleting user configuration, and report the actual path. This is a necessary configuration-path correction for the verified adapter, not permission to migrate/remove unrelated settings or automatically uninstall anything. Do not falsely promise that native Pi imports root `.mcp.json`.

The extension's independent HTTP bookkeeping must consume the file generated by credential seeding, not require a newly undocumented URL export. With `CHORUS_API_KEY` exported and `CHORUS_URL` absent, fresh legacy setup must discover the URL from the adapter5 primary, including a custom agent directory. A retained old global `mcp.json` must not shadow that legacy primary. Native hosts must retain native config selection rather than accidentally using stale adapter configuration. Explicit environment connection values retain precedence; malformed/unreadable/partial candidates must not crash discovery or cause unresolved environment templates to be sent as credentials. Native project `.pi/mcp.json` discovery is not expanded by this bounded correction. This closes aggregate-review finding `B1-legacy-config-runtime-discovery`; the integration regression must generate configuration with the real CLI writer and exercise the actual extension without exporting its URL independently.

## Tool resolution and division of ownership

Generic normalization supports bare `chorus_*`, legacy `chorus_chorus_*`, and native `mcp__chorus__chorus_*`. Validate primitive strings and return null for invalid inputs. Any retained non-workflow gateway helper may extract a string `input.tool` only for known wrappers, and must remain separate from workflow event resolution. `resolveChorusToolName` at the workflow event boundary inspects only `event.toolName`, never reads `input` (including getters), and does not maintain a gateway whitelist. Preserve the related implementation's decoy-input and throwing-getter regressions; bare gateway outer names must not trigger reviewer reminders.

Approved Proposal `05a19157-d028-47a1-8887-c05c33b3274a` owns arbitrary-prefix exact suffix matching for three workflow actions and the associated Pi/dsh reminder tests. Its persistent Design v6 and completed follow-up task confirm human-selected outer-only event resolution and actual Pi 1.0.2 native codemode child events. This proposal does not reimplement that logic or modify dsh. Reconcile existing changes after approval, retain the broader workflow matcher, and add focused generic non-workflow normalization tests. Reuse the completed native host fixture/evidence when available; do not restore legacy workflow gateway parsing from this checkout's older uncommitted patch.

Pi package skills/worker instructions make native tools the default, retaining adapter examples as the legacy branch. Audit package metadata, README, CONNECT_PI, install/upgrade/credential diagnostics, and all seven skill surfaces for unconditional adapter assumptions; only edit applicable Pi guidance, not unrelated host tool names.

Offline tests cover 0.87.1/0.98.9, boundary 0.99.0, 0.99.2, 1.0.2, multi-digit versions, optional v/build metadata, prereleases, unknown/error probes; native fresh/repeat/update with and without adapters; legacy fresh/partial/update; pinned and object package entries; malformed settings; missing Pi; failure reporting; preserved credentials and unrelated settings. Run CLI focused suites and Pi `test/all.sh` plus package validation/pack checks with repository commands.

The package task's local-fixture host matrix is mandatory and requires no production credentials/provider. For additional production-provider smoke use temporary `PI_CODING_AGENT_DIR` and an isolated project, never the user's active settings. On native Pi verify tools connect without adapter and record actual tool names using an authorized read-only call; optionally repeat against legacy transport. Do not submit/verify real workflow entities solely for a smoke test. Missing production auth/network is reported as unverified for that optional smoke only; it cannot waive missing mandatory packaged-artifact compatibility tests.
